# RACObjC on GNUstep

RACObjC builds as a shared library (`libRACObjC.so`) on GNUstep, for example
on FreeBSD (including Gershwin) or Linux. Apple platforms are unaffected: they
keep using CocoaPods/Xcode, and every source change is behind `#ifdef GNUSTEP`
or a guard that is already true on Apple (`OS_OBJECT_USE_OBJC`,
`#ifndef NS_ERROR_ENUM`).

## Requirements

- clang
- libobjc2 (the `ng` runtime: `-fobjc-runtime=gnustep-2.x`), with its
  embedded blocks runtime or an external one (see *Block IMPs* below)
- gnustep-make, gnustep-base
- libdispatch (swift-corelibs-libdispatch)
- gnustep-base built **with libdispatch run loop integration**, so that
  `RACScheduler.mainThreadScheduler` (the main dispatch queue) is drained by
  `NSRunLoop`. Check with:

  ```sh
  grep GS_USE_LIBDISPATCH_RUNLOOP $(gnustep-config --variable=GNUSTEP_SYSTEM_HEADERS)/GNUstepBase/GSConfig.h
  ```

  It should print `1`. Gershwin's build (gershwin-developer) builds libdispatch
  before gnustep-base, so this works out of the box.

- [gnustep/tools-xctest](https://github.com/gnustep/tools-xctest), only for
  `gmake check` (CI uses its commit `5c84fc3` of 2026-10-05)

Supported CPUs: aarch64 and x86_64 (see *rac_signalForSelector:* below).

## Build, test, install

From `Core/RACObjC`, after sourcing `GNUstep.sh` (on FreeBSD use `gmake`):

```sh
gmake                 # obj/libRACObjC.so
gmake check           # run the smoke tests and the specs (see Tests below)
GNUSTEP_INSTALLATION_DOMAIN=USER gmake install   # into ~/GNUstep
```

## Using it

```objc
#import <RACObjC/RACObjC.h>
```

```make
# in your GNUmakefile
MyApp_GUI_LIBS = -lRACObjC -ldispatch
ADDITIONAL_OBJCFLAGS += -fobjc-arc -fblocks
```

## What is different on GNUstep

| Area | Apple | GNUstep |
|---|---|---|
| `rac_signalForSelector:` | installs `_objc_msgForward` | installs `RACObjCMsgForward` (see below) |
| Swizzled `-dealloc`, `-forwardInvocation:`, `-respondsToSelector:`, `-class`, `-methodSignatureForSelector:` | block IMPs | plain functions with per-class tables (see *Block IMPs*) |
| Super calls in swizzled `-dealloc` / `-methodSignatureForSelector:` | `objc_msgSendSuper` | `objc_msg_lookup_super` |
| CoreFoundation (`CFArray`, `CFBinaryHeap`, `CFBridging*`) | system CF | small hidden Foundation-based shims (`RACCFShims.m`) |
| DTrace probes (`*.d`) | generated by Xcode | no-op headers (`shim/`) |
| libdispatch objects | ObjC objects (ARC) | C objects; retained/released by hand |
| `+[NSData rac_readContentsOfURL:options:scheduler:]` | uses `options` | `options` ignored (no `NSDataReadingOptions`) |
| `+[NSURLConnection rac_sendAsynchronousRequest:]` | `sendAsynchronousRequest:` | synchronous request on a private `NSOperationQueue` |

### rac_signalForSelector:

libobjc2 has no `_objc_msgForward`. Instead, gnustep-base hands out a
forwarding IMP per call (via the `__objc_msg_forward2` hook), and that IMP is a
temporary libffi closure that dies with the current autorelease pool, so it
cannot be stored in a method table. `GNUstep/RACObjCMsgForward.c` provides a
permanent IMP that saves the argument registers, asks the hook for the
forwarding IMP, restores the registers and tail-calls it, which is what the
runtime itself does for an unknown selector. It is written for aarch64 and
x86_64. Struct, union and vector return types are rejected, the same as on Apple.

### Block IMPs

On Apple platforms RACObjC swizzles methods with `imp_implementationWithBlock()`
IMPs that capture per-class state: `-dealloc`, once per class
(`rac_willDeallocSignal`, `rac_deallocDisposable`, and everything built on
them), and five methods per class for `rac_signalForSelector:`. libobjc2
can't be relied on for those:

- Since [gnustep/libobjc2#355](https://github.com/gnustep/libobjc2/pull/355),
  which came after 2.3, a libobjc2 built against an external blocks runtime
  has no `imp_implementationWithBlock()`. Gershwin's gershwin-developer builds
  it that way (as of its 2026-07-26 pins).
- libobjc2 (2.3 and master as of 2026-11) hands out only one page of them per
  process: 128 on aarch64, 256 on x86_64. The next one returns a bad IMP that
  crashes when called
  ([gnustep/libobjc2#438](https://github.com/gnustep/libobjc2/pull/438) is an
  open fix).

So on GNUstep each of those methods is one plain function, and what the
blocks captured lives in per-method tables (`GNUstep/RACSwizzleTable.h`).
Once both libobjc2 issues are fixed, building with `-DRAC_USE_BLOCK_IMPS=1`
goes back to block IMPs, as on Apple platforms.

### Workarounds for gnustep-base bugs

Both are still present in gnustep-base master (checked 2026-11-02):

- `NSDate` small-object (tagged) dates cannot represent an interval of exactly
  `0.0` (it reads back as `2.0`). `RACTestScheduler` therefore numbers directly
  scheduled blocks from 1 instead of 0.
- `-enumerateSubstringsInRange:options:` with
  `NSStringEnumerationByComposedCharacterSequences` runs past the end of the
  range and throws `NSRangeException`. `RACStringSequence -array` walks the
  composed character sequences by hand.

## Tests

`gmake check` runs two things:

- `RACSmokeTests`: 47 checks of signals, subjects, sequences,
  disposables, schedulers (including the main queue), KVO,
  `RAC()`/`RACChannelTo`, `rac_signalForSelector:` (integer, double, object
  and stack arguments, undefined selectors, protocols), dealloc swizzling
  (including 300 swizzled classes, past libobjc2's block IMP limit),
  `RACCommand` and the Foundation categories.
- The specs in `Core/RACObjCTests`, the same files as on Apple platforms. Quick
  and Nimble need Swift, which can't call Objective-C off Apple platforms, so
  `Tests/QuickNimble/` reimplements the Objective-C API of Quick 5 and
  Nimble 10 that the specs use. Each example becomes an XCTest test method
  with the same name as on Apple platforms, run by tools-xctest's `xctest`.
  The specs are compiled from copies in `Tests/derived_src/specs`, where only
  the `@import Quick;` and `@import Nimble;` lines change; compiler errors and
  test failures point at the original files.

The Swift spec (`RACSwiftBridgingSpec.swift`) doesn't run. The specs listed in
[`Tests/KnownFailures.md`](Tests/KnownFailures.md) fail on GNUstep, grouped
with what's known about why. A listed spec still runs, but its failures are
only logged. If one starts to pass, or the list names a test that doesn't
exist, the run fails, so the list stays accurate. A `skip` entry doesn't run
at all, and an entry prefixed with `aarch64` or `x86_64` only applies on that
CPU. Entries are list items holding only a code span, so the file reads as
an ordinary Markdown document.

To run one spec, or one test:

```sh
cd GNUstep/Tests
LD_LIBRARY_PATH=../../obj xctest -XCTest RACSignalSpec RACObjCSpecs.bundle
LD_LIBRARY_PATH=../../obj xctest -XCTest RACSignalSpec.memory_management__should_dealloc_signals_if_the_signal_immediately_completes RACObjCSpecs.bundle
```
